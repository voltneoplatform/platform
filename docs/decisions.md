# Technical decisions

Business decisions live in the Foundation's Decision Log (D1–D52). This file
records technical choices made while building, so they are not changed silently.
Status labels follow the project convention: CONFIRMED (founder decided),
PROPOSED (Claude recommends), ASSUMED (working assumption).

| #   | Decision                                                                                                                                                                                                                                                                                | Why                                                                                                                                                                                                                                                                                                        | Status                                     |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| T1  | TypeScript everywhere: NestJS, PostgreSQL + Prisma, BullMQ/Redis, Next.js, React Native (Expo), one pnpm monorepo                                                                                                                                                                       | Founder decision, 22 Oct 2026                                                                                                                                                                                                                                                                              | CONFIRMED                                  |
| T2  | NestJS 12, Prisma 7.10, Next.js 16, React 19, TypeScript 5.9, Node.js 22.12+                                                                                                                                                                                                            | Current stable releases. TypeScript 7 (the new native compiler) is not adopted yet because NestJS depends on legacy decorator metadata and that combination has not been verified for this project; ts-jest and other tooling also still declare TypeScript below 7. Prisma 8 is still a release candidate | PROPOSED                                   |
| T3  | The API compiles to CommonJS while NestJS 12 ships as ES modules; Node.js 22.12+ loads them natively (`require(esm)`)                                                                                                                                                                   | Keeps Prisma's generated client and tooling simple; no runtime cost                                                                                                                                                                                                                                        | PROPOSED                                   |
| T4  | Vitest with SWC for API tests (not Jest)                                                                                                                                                                                                                                                | Jest on Node 22 cannot load ES-module-only NestJS 12; SWC emits the decorator metadata Nest needs                                                                                                                                                                                                          | PROPOSED                                   |
| T5  | Prisma 7 with the `pg` driver adapter and `prisma.config.ts`                                                                                                                                                                                                                            | Prisma 7's supported setup; no native query engine to ship                                                                                                                                                                                                                                                 | PROPOSED                                   |
| T6  | Rules Prisma cannot express (check constraints, the append-only audit trigger) are added by hand at the end of migration files. CI applies all migrations to a fresh database with `prisma migrate deploy` and fails if `prisma migrate diff` finds any difference from `schema.prisma` | Keeps the database as the last line of defence while proving migrations and schema never drift                                                                                                                                                                                                             | PROPOSED                                   |
| T7  | Staff sign in with a 6-digit one-time code by SMS or email; no passwords                                                                                                                                                                                                                | Spec section 7; field staff use phones. Codes: 5-minute expiry, 5 attempts, single use, HMAC-hashed and bound to the challenge, 30-second resend cooldown                                                                                                                                                  | PROPOSED                                   |
| T8  | Access token (JWT, HS256, 15 minutes) plus rotating single-use refresh token. Reuse of a used refresh token revokes the whole login. Idle limit 30 minutes, absolute limit 12 hours                                                                                                     | Spec section 7 (admin sessions expire after inactivity). Short access tokens limit damage from a leak                                                                                                                                                                                                      | PROPOSED; idle and absolute limits ASSUMED |
| T9  | The admin panel receives the refresh token only as an httpOnly, SameSite=Strict cookie scoped to `/v1/auth`, and calls the API through its own origin. Apps receive it in the response body for secure device storage                                                                   | Page scripts can never read the refresh token                                                                                                                                                                                                                                                              | PROPOSED                                   |
| T10 | Every authenticated request re-checks the session and the staff member's current role in the database                                                                                                                                                                                   | Logout, deactivation and role changes apply at once rather than when a token expires                                                                                                                                                                                                                       | PROPOSED                                   |
| T11 | Roles and permissions are defined in code (`packages/shared/src/roles.ts`) for the MVP                                                                                                                                                                                                  | Spec says roles are configurable; a database-backed role editor can be added later without changing call sites, because everything checks permissions, not role names                                                                                                                                      | PROPOSED                                   |
| T12 | Field roles (agent, technician, recovery) cannot sign in to the admin panel; head-office roles cannot use the Field App                                                                                                                                                                 | Matches the "Uses" column in spec section 2. Until the Field App exists (M5), head office does field steps from the admin panel as the spec allows                                                                                                                                                         | PROPOSED                                   |
| T13 | OTP delivery sits behind an adapter: `log` (development), `memory` (tests). The API refuses to start in production without a real provider                                                                                                                                              | No SMS/email provider chosen yet (founder decision before M2 goes live)                                                                                                                                                                                                                                    | PROPOSED                                   |
| T14 | The admin panel uses neutral placeholder design tokens in one CSS file                                                                                                                                                                                                                  | The Brand Kit (Phase 3) does not exist yet; replacing the tokens restyles every screen                                                                                                                                                                                                                     | ASSUMED                                    |
| T15 | Code is formatted with Prettier and linted with ESLint (bug-catching rules only); both run in CI                                                                                                                                                                                        | Added ESLint in M1 as planned                                                                                                                                                                                                                                                                              | PROPOSED                                   |

## Milestone M1 (set-up data)

| #   | Decision                                                                                                                                                                                                                                         | Why                                                                                                                                                                                 | Status                                                            |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| T16 | Plan prices form a grid: each plan version has its own down payment and instalment per eligible battery type; the number of instalments is per version                                                                                           | The Foundation (sections 5 and 9) proposes a price grid; the spec's single price per version is the special case of entering the same figures for every type.                       | CONFIRMED (founder, 23 Oct 2026)                                  |
| T17 | Cost floor = purchase cost + per-battery allowances for GPS, service, financing, collection and expected losses, entered by head office per battery type. Blank allowances count as zero                                                         | No unit economics model exists yet; this follows the Foundation's pricing-logic list and is never below the purchase cost. Replace the allowances with model outputs when it exists | CONFIRMED (founder, 23 Oct 2026)                                  |
| T18 | "Two head-office users approve an exception" (spec rule 2) is implemented as maker-checker: the publisher asks, and a different plan manager or super admin approves                                                                             | Same pattern as every other two-person action (D19, D26)                                                                                                                            | PROPOSED; founder may ask for two approvers besides the publisher |
| T19 | Every plan version copies the non-payment terms in force when it is created (5-day grace, ₹100/day, 60-day cap), so a signed driver keeps them if policy changes                                                                                 | Spec rule 1 (versions never change) and D33/D38                                                                                                                                     | PROPOSED                                                          |
| T20 | Published plan versions, their prices, battery cost history and custody history are protected by database triggers against change                                                                                                                | Spec rules 1 and 17; the database is the last line of defence                                                                                                                       | PROPOSED                                                          |
| T21 | Plan names: all three languages required, at most 32 characters, no two non-retired plans share a name in any language (case-insensitive), and claim words are blocked (cheapest, best, free, guaranteed and Bengali/Hindi equivalents)          | D27 and Foundation naming rules. The Bengali and Hindi blocked words need review by a native speaker                                                                                | PROPOSED                                                          |
| T22 | Aadhaar: only the last 4 digits and a keyed fingerprint (for duplicate checks) are stored, never the full number; a database check enforces it. Other ID numbers are encrypted with AES-256-GCM                                                  | Conservative until legal item L7 (KYC method) is answered. Not a legal conclusion                                                                                                   | PROPOSED; REQUIRES VALIDATION (L7)                                |
| T23 | KYC files and owner consent forms are stored privately and opened only through signed links that expire after 5 minutes; every view and full-number reveal is written to the audit log                                                           | Spec section 7. Local-disk storage for development; a cloud storage adapter follows the hosting decision                                                                            | PROPOSED                                                          |
| T24 | Duplicate phone numbers, vehicle registrations and ID documents are flagged, not blocked: staff must confirm, and the confirmation is audited                                                                                                    | Spec module 5 ("flagged"); renter-drivers may share a phone or a vehicle                                                                                                            | PROPOSED                                                          |
| T25 | Readiness for an agreement: driver 18 or older, identity document verified, proof of address verified, driver photo verified, vehicle recorded, owner's consent uploaded for renter-drivers, nominee recorded. M2 will require it before signing | Foundation section 7 step 3, D21, D49, D52                                                                                                                                          | PROPOSED                                                          |
| T26 | KYC verification and full ID access: operations manager and super admin. Support and field agents see masked numbers only; field agents can upload but not open files afterwards                                                                 | Spec section 2 (support cannot see full IDs)                                                                                                                                        | PROPOSED                                                          |
| T27 | Head office can only move batteries between in stock and under repair (and out of recovered). Installed, recovered and transferred are set by their own workflows in M2-M4; retirement needs a second person                                     | Spec maker-checker list includes retiring a battery                                                                                                                                 | PROPOSED                                                          |
| T28 | A vehicle needs a registration number or, failing that, a chassis number                                                                                                                                                                         | Some totos may be unregistered                                                                                                                                                      | ASSUMED                                                           |
